# 开发工作流约定

> 记录本项目如何用「OpenClaw 驱动 DSH」完成开发，以及 git、模块、工作区的约定。

## 1. 交互链路

```
用户 ↔ OpenClaw ↔ DSH(headless)
```

OpenClaw 通过 `dsh --profile headless "任务描述"` 驱动 DSH 生成代码，整理后写文件、验证、回报用户。

## 2. 每个功能节点从一次 git 提交开始

- 每个功能节点（模块）开始时，先做一次 git 提交作为干净基线
- 该功能节点从「干净的 git 状态」开始开发，出错可回退到这个基线
- 完成后再做一次提交，形成「基线提交 → 开发 → 完成提交」的节奏

## 3. Git 管理

- 仓库根：E:\WordCut
- 每个功能节点完成后一个 commit
- commit 信息格式：`动词 + 模块 + 说明`（如 `feat(对齐): 词级时间戳模块`）
- 单人毕设，直接在 main 顺序提交即可；重大实验分支可开 feature/xxx

## 4. DSH 工作区设定

- DSH 的 workspace = 运行 dsh 命令时的当前目录
- 生成后端代码：workdir 设 `E:\WordCut\src`
- 生成前端代码：workdir 设 `E:\WordCut\frontend`
- 让 DSH 只在其工作区内操作，不越界

## 5. 前端美化

- 前端界面美化时，让 DSH 下载相关 skill（前端 UI 相关）
- 由 OpenClaw 驱动 DSH 完成，不手动堆 CSS

## 6. 验证闭环

```
DSH 生成代码 → OpenClaw 写文件 → 跑不变量测试 / 实际运行 → 不过则打回 DSH 重生成
```
